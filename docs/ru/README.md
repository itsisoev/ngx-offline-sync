> **Offline-first синхронизация HTTP-запросов для Angular.**

`ngx-offline-sync` — open-source библиотека для Angular, которая помогает приложениям корректно работать при временной потере интернет-соединения.

Когда приложение находится офлайн, поддерживаемые HTTP-запросы автоматически помещаются в локальную очередь и сохраняются в **IndexedDB**. После восстановления соединения библиотека самостоятельно запускает синхронизацию и выполняет накопленные запросы.

Вам не нужно создавать отдельную очередь, самостоятельно управлять IndexedDB или писать собственную логику восстановления соединения — библиотека берёт эту работу на себя, сохраняя привычный API Angular `HttpClient`.

## Как это работает

### Онлайн

<p align="center">
  <img src="../assets/gifs/01-online.gif" alt="ngx-offline-sync — работа без сети" />
</p>

При наличии интернет-соединения запросы выполняются обычным способом через Angular `HttpClient`.

```
HttpClient
    ↓
offlineSyncInterceptor
    ↓
HTTP request
    ↓
Server
```

Запрос отправляется напрямую, без задержек и дополнительной логики.

### Офлайн

<p align="center">
  <img src="../assets/gifs/02-offline.gif" alt="ngx-offline-sync — синхронизация после восстановления сети" />
</p>

Когда соединение отсутствует, поддерживаемые запросы не теряются. Они сохраняются локально и помещаются в очередь ожидания.

```
HttpClient
    ↓
offlineSyncInterceptor
    ↓
QueueService
    ↓
IndexedDB
    ↓
PENDING
```

Запрос сохраняется локально и ожидает восстановления соединения. Пользователь не видит ошибки сети — запрос просто переходит в статус `PENDING`.

### Восстановление соединения

<p align="center">
  <img src="../assets/gifs/03-sync.gif" alt="ngx-offline-sync — синхронизация после восстановления сети" />
</p>

После восстановления соединения библиотека автоматически начинает обработку очереди и синхронизирует сохранённые запросы.

```
NetworkStatusService
    ↓
SyncCoordinatorService
    ↓
SyncService
    ↓
SYNCING
    ↓
HTTP request
    ↓
COMPLETED
```

Очередь обрабатывается автоматически, без участия разработчика — `NetworkStatusService` замечает восстановление сети и запускает синхронизацию.

## Возможности

* **Автоматическая очередь запросов** — поддерживаемые HTTP-запросы автоматически сохраняются при отсутствии сети.
* **IndexedDB** — очередь хранится локально и сохраняется между перезагрузками страницы.
* **Автоматическая синхронизация** — накопленные запросы обрабатываются после восстановления соединения.
* **Batch processing** — несколько запросов могут обрабатываться параллельно с помощью `batchSize`.
* **Повторные попытки** — неуспешные запросы могут автоматически повторяться согласно политике повторных попыток.
* **Angular HTTP interceptor** — библиотека интегрируется непосредственно с `HttpClient`.
* **Без дополнительного API** — для отправки запросов используется обычный `HttpClient`.
* **Настраиваемая синхронизация** — поведение очереди и синхронизации можно изменять через конфигурацию.
* **Настраиваемое логирование** — уровень логирования можно выбрать с помощью `LogLevel`.
* **Несколько языков логирования** — сообщения поддерживают английский и русский языки через `LogLanguage`.
* **События логирования** — библиотека предоставляет типизированные события для отслеживания состояния очереди и синхронизации.
* **Статистика синхронизации** — библиотека собирает информацию о количестве обработанных, успешных, неудачных и повторно отправленных запросов.
* **Настраиваемый Log Transport** — стандартный `ConsoleLogTransport` можно заменить собственной реализацией через `LOG_TRANSPORT`.

## Поддерживаемые HTTP-методы

На данный момент библиотека помещает в очередь следующие HTTP-методы:

* `POST`
* `PUT`
* `PATCH`
* `DELETE`

`GET`-запросы не сохраняются в offline queue. Подробнее см. раздел [Ограничения](#ограничения).

## Подключение

Добавьте `provideOfflineSync()` и `offlineSyncInterceptor` в конфигурацию приложения:

```typescript
import { ApplicationConfig } from '@angular/core';
import {
  provideHttpClient,
  withInterceptors,
} from '@angular/common/http';

import {
  provideOfflineSync,
  offlineSyncInterceptor,
} from 'ngx-offline-sync';

export const appConfig: ApplicationConfig = {
  providers: [
    provideOfflineSync(),

    provideHttpClient(
      withInterceptors([
        offlineSyncInterceptor,
      ]),
    ),
  ],
};
```

После подключения библиотека самостоятельно управляет очередью, локальным хранилищем, синхронизацией и повторными попытками. Дополнительная регистрация внутренних сервисов не требуется.

> `provideOfflineSync()` также принимает необязательный объект конфигурации (например, `batchSize`). Полный список опций — в разделе [Конфигурация](#конфигурация).

## Использование

Для отправки запросов не требуется специальный API. Используйте обычный Angular `HttpClient`:

```typescript
this.http.post('/api/products', product).subscribe();
```

* При наличии сети запрос выполняется как обычно.
* Если соединение отсутствует, поддерживаемый запрос автоматически сохраняется в очереди и будет обработан после восстановления сети.

Никакой дополнительной обёртки, отдельного сервиса или ручного управления очередью не требуется — `offlineSyncInterceptor` перехватывает запрос до того, как он уйдёт по сети, и сам решает, как с ним поступить.

## Статусы запросов

Каждый запрос в очереди имеет один из следующих статусов:

| Статус      | Описание                    |
|-------------|-----------------------------|
| `PENDING`   | Запрос ожидает выполнения   |
| `SYNCING`   | Запрос выполняется          |
| `COMPLETED` | Запрос успешно выполнен     |
| `FAILED`    | Запрос не удалось выполнить |

### Основной жизненный цикл

```
PENDING → SYNCING → COMPLETED
```

Запрос попадает в очередь (`PENDING`), затем начинает выполняться (`SYNCING`), и при успехе получает финальный статус `COMPLETED`.

### При ошибке

```
SYNCING → RetryPolicy → PENDING → Retry
```

Если запрос завершился ошибкой, решение о повторной попытке принимает `RetryPolicy` — см. раздел [Повторные попытки](#повторные-попытки).

### Если запрос больше не должен повторяться

```
SYNCING → FAILED
```

Когда `RetryPolicy` решает, что дальнейшие попытки бессмысленны (например, превышен лимит попыток), запрос переходит в `FAILED` и остаётся в этом статусе.

## Повторные попытки

Если синхронизация завершается ошибкой, библиотека передаёт ошибку в `RetryPolicy`.

Политика определяет:

* нужно ли повторить запрос;
* задержку перед следующей попыткой;
* когда запрос должен получить статус `FAILED`.

### Жизненный цикл при ошибке

```
SYNCING → Request failed → RetryPolicy → PENDING → Retry
```

После неудачного выполнения запрос возвращается в `PENDING` и дожидается следующей попытки синхронизации.

### После успешной попытки

```
PENDING → SYNCING → COMPLETED
```

### Если попытки исчерпаны

```
SYNCING → Request failed → FAILED
```

Как только количество попыток превышает допустимый лимит, запрос окончательно переходит в `FAILED` и больше не участвует в синхронизации.

## Архитектура

Библиотека разделена на несколько основных компонентов:

```
NetworkStatusService
        │
        ▼
OfflineSyncInterceptor
        │
        ▼
QueueService
        │
        ▼
IndexedDbStorage
        │
        ▼
SyncCoordinatorService
        │
        ▼
SyncService
        │
        ├── RetryPolicy
        │
        └── HttpClient
```

### Основные компоненты

**offlineSyncInterceptor**
Перехватывает HTTP-запросы и определяет, необходимо ли поместить запрос в очередь.

**NetworkStatusService**
Отслеживает состояние интернет-соединения и сообщает библиотеке о восстановлении сети.

**QueueService**
Управляет очередью запросов: добавлением, получением, обновлением и удалением элементов.

**IndexedDbStorage**
Использует IndexedDB для постоянного локального хранения очереди.

**SyncCoordinatorService**
Отслеживает восстановление соединения и запускает синхронизацию очереди.

**SyncService**
Получает запросы из очереди, выполняет их через `HttpClient` и обновляет их статус. Именно здесь применяется настройка [batchSize](configuration/batch-size.md), определяющая, сколько запросов обрабатывается параллельно.

**RetryPolicy**
Определяет правила повторного выполнения неуспешных запросов — см. раздел [Повторные попытки](#повторные-попытки).

## Ограничения

* Библиотека предназначена для синхронизации следующих HTTP-методов: `POST`, `PUT`, `PATCH`, `DELETE`.
* `GET`-запросы не помещаются в offline queue.
* Очередь хранится локально в IndexedDB браузера.

* Улучшение обработки ошибок и сетевых состояний
* Расширенные возможности настройки IndexedDB
